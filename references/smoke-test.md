# lhg-secure 标准冒烟用例

自检命中疑似缺陷、或用户要求验证时运行。以下 4 个用例全部通过才算冒烟通过。
"运行"指按 SKILL.md 四步流程对 fixture 实际执行一次审计（人工或 agent 按流程走），对照"通过标准"判定。

## 用例 S-1：已知漏洞不漏报（fixture A）

对 `references/fixtures/vuln_app.py` 走完全流程。

通过标准（缺一项即失败）：
- 输出 5 条 finding，不多不少：
  - `vuln_app.py:22` SQL 注入 → **高**（username 来自 Web 表单 → 字符串拼接进 SQL → `SELECT *` 批量泄露；可远程触发+低权限，数据流完整）
  - `vuln_app.py:29` 命令注入（shell=True） → **高**（host 来自 Web 表单 → 拼进 shell 命令 → RCE）
  - `vuln_app.py:12` 硬编码生产密钥 → **中**（需拿到源码/制品才可利用，属"特定条件"；泄露即完全失陷）
  - `vuln_app.py:36` MD5 口令比对 → **中**（需先拿到 hash 才可利用）
  - `vuln_app.py:42` 路径穿越 → **中**（name 来自 Web 表单；若确认该函数暴露给远程输入则升为高，须在定级依据中注明该条件）
- 每条 finding 都有：证据链（输入→…→危险操作）、定级依据、修复建议。
- 报告含"未覆盖范围声明"（如：未做依赖 CVE 核验、未审计调用方鉴权）。

## 用例 S-2：误报陷阱不夸大（fixture B）

对 `references/fixtures/false_positive_trap.py` 走完全流程。

通过标准：
- 第 2 步应收集到 4 个候选（PASSWORD_LABEL 变量名、execute 调 SQL、subprocess、literal_eval）。
- 第 3 步对抗验证后，4 个**全部被推翻**，输出 0 条 finding。
- "误报说明"逐条写清推翻理由（参数化查询 / 无 shell=True 列表传参 / UI 文案非密钥 / literal_eval 只解析字面量）。
- 若有任一候选被写成 finding，即失败（夸大）。

## 用例 S-3：去重生效

在 S-1 审计中，`vuln_app.py:22` 的 SQL 注入会被维度①（注入类）和维度⑨（危险 API 设计）同时命中。

通过标准：最终报告只出现一次（按 `类别:文件:行` 去重，保留"注入类"），不出现重复两条。

## 用例 S-4：强制门禁

检查 S-1 的报告是否通过门禁评审：① 每个 finding 有完整证据链；② 每个 finding 写了定级依据；③ 误报说明非空（fixture A 无误报候选时写"本次无误报候选"）；④ 覆盖率声明已写。缺一项即失败。
