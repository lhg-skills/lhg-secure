# 误报判定清单

第 3 步对抗验证时用。核心问题只有一个：**从不可信输入到危险操作的链路，是否完整且无人拦截？**

## 推翻候选的常见理由（可直接写入"误报说明"）

1. **输入不可达**：参数只来自可信内部调用/常量，外部输入到不了。
2. **已被拦截**：中间有参数化查询、转义、白名单校验、权限检查，链路已断。
3. **API 安全用法**：如 `subprocess.run` 无 `shell=True` 且参数为列表；`ast.literal_eval` 而非 `eval`。
4. **死代码/测试桩**：从未被实际调用，或只在测试/管理内网环境出现（可达性降级，不直接判死刑，注明即可）。
5. **名不副实**：变量名含 password/key/token 但实际是 UI 文案、字段名、占位符。
6. **弱算法的安全用途**：MD5/SHA1 仅用于非安全场景（如缓存键、文件去重标识），且注释/上下文可证无口令/签名用途。注意：拿不准的一律按可疑处理，不硬判误报。

## 不许判误报的情况

- "看着像内部函数"但没证据证明外部到不了——没证据就不能推翻。
- "应该有 WAF/网关挡住"——纵深防御不算拦截证据，代码层该修还得报（可降级，不可抹掉）。
- 链路有一环看不懂——标"无法验证"，进覆盖率声明，不判误报也不判 finding。

## 写法示例

- 候选 `fp_trap.py:14 cur.execute(...)`：推翻。使用了参数化查询 `?` 占位，SQL 结构与数据分离，注入链路不存在。
- 候选 `fp_trap.py:19 subprocess.run(...)`：推翻。无 `shell=True`，参数以列表传递且经 `shlex.split` 切分，命令注入链路不存在。
